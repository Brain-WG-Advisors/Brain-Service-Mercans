## Inputs

- The flagged list: `04-output/final-prep/<SPEC>-pass3-flagged.json` (cells with "Rule to be set at implementation", "configuration parameter / supplied at implementation", scope_manifest, CO-GAP-xx, CCG control B7, the listed defects, and Payroll Scope Summary rows with an empty REPORT? or NOTES cell). Also read the rest of the sheet for the same wording the regex may have missed ("to be defined", "pending", "open point", "at implementation").

## Rule 1. No "rule to be set" / "to be defined" / "configuration parameter supplied at implementation" wording
For every such sentence, one of three outcomes:
a) The rule is already defined (by this session's rules, the spec's own other cells, or the rules in "Additional rules" below): write the rule, with its source.
b) The point depends on how a wage type is classified: write the general rule and state that the classification of each wage type comes from the Wage Type Catalogue (WTC) attribute (e.g. "Habitual bonuses are reported in casilla 36 and non-habitual bonuses in casilla 46; the habitual attribute of each bonus wage type comes from the WTC."). Do not say the point is pending, open, to be confirmed or to be set.
c) No rule exists and it is not a wage-type attribute: remove the sentence from the spec (keep the rest of the cell) and list the item in `moved_to_open_points` with sheet, cell, field id and the exact question. If the whole cell was the open sentence (e.g. a Report Matrix row), replace it with a neutral statement of what the spec does define, or clear the cell if nothing remains.
Treat "configuration parameter supplied at implementation" sentences the same way: a mapping table that the implementation configures from master data is a legitimate rule if stated as such ("The Employee Group to contributor-type mapping is maintained as a configuration table"), but "to be supplied/agreed/confirmed at implementation" wording goes.
