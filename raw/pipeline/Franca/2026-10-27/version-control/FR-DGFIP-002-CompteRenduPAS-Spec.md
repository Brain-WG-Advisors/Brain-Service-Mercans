|  | The honest limit of this specification | The CRM PAS RECORD LAYOUT WAS NOT OBTAINED. It is not in the DSN cahier technique, not in NEOReS - which expressly excludes the PAS returns from its scope - and the published note describing it was not retrievable in readable form for this build. Part A of the spec sheet therefore states the structure at BLOCK level only, from the platform's service description, and column H records the gap on every row rather than carrying an invented path. Sheet 9 carries no fabricated sample for the same reason: this return's only consumer is a parser, so a fabricated instance would be built against directly. What IS exact is Part B, the consumption side, because the DSN norm defines those rubriques precisely - which is enough to build the payroll behaviour correctly, and is not enough to build the parser. That distinction is stated rather than blurred. |  |  |  |
|  | Confidentiality is a design constraint, not a policy | The employer receives a rate and a type code and nothing else. It cannot learn the employee's household situation and cannot tell whether the employee has opted for a neutral rate. That confidentiality is what made the scheme acceptable, and it is defeated not by malice but by well-intentioned features - a rate-history screen, an 'unusual rate' flag, a distribution report by team. The File Structure sheet names these explicitly so they can be caught at design review rather than after. |  |  |  |
